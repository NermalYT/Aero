# Aero 1.2: integrations and workspaces

Aero 1.2 builds other projects' functions into Aero itself. Each one is an **integration pack**
(`aero/integrations/*.py`): its tools sit in Aero's tool registry with the same permissions, evidence notes, Stop and
autonomy modes as every other tool; its skills sit in `aero/skills_builtin/packs`; what it needs on the computer
(an SDK, a binary, a model, a server) is checked and, where Aero can, installed into Aero's own folder
(`data/toolchains`) after the user says yes. Nothing is added to the system PATH.

Packs are grouped into **workspaces**, a panel beside the chat (sidebar, *Workspaces*): Code, Mobile apps, Create,
Diagrams, Review & test, Debug & reverse, Finance, Library, Memory+, Big models. A request that needs a pack opens its
workspace by itself: `integrations.context` matches the request against each pack's patterns (no model call, a few
milliseconds), puts a line into the turn context ("Integrations for this request: Flutter …: tools flutter_create,
flutter_preview …; not installed yet: Flutter SDK, offer integration_install"), adds the pack's tools to the ones the
model sees and sends the UI a `workspace` event. The router's own catalog leaves the integration tools out (53 tools
instead of 94), so routing stays as fast as before.

## What is not built in, and why

- **ArtCraft's generation**: its image/video/3D generation goes to paid cloud services, and several of its clients
  drive web apps with browser cookies against their terms. Aero's Create workspace generates locally instead.
- **Flutter on iOS from Windows**: Flutter iOS builds need a Mac with Xcode. SwiftPM iOS apps can be built from
  Windows through xtool in WSL, after the user does Apple's own steps.
- **Native emulator windows**: Android/iOS emulators are their own windows; the live preview inside Aero is the web
  build of the same app.
- **RAD Debugger's window**: it has no headless engine, so its window opens during a debugging session while Aero
  drives it and reads the state back.
- **Paid data**: the financial-services repository's data connectors (S&P Global, FactSet, PitchBook …) need the
  user's own provider accounts; they are not included.
- **Disassemblers**: rea's native analysis needs Ghidra, Hopper or IDA, which the user installs.
- **Model quality**: open-code-review, e2e and Hindsight publish results with hosted models; how well a small local
  model does in them is not measured by those projects.

## Safety

- Installs go through the `setup` permission (ask by default) or a workspace button, show their size first, and land
  in `data/toolchains`; downloads are checked against the checksums the projects publish where they publish them.
- Strict offline refuses every download and every program that would reach the network (npm, pip, flutter pub).
- The integration file endpoint only serves Aero's own diagrams and images folders, with a sandboxing
  Content-Security-Policy for HTML/SVG; the workspace "run" endpoint only runs integration tools, never file,
  shell, desktop or browser tools.
- RAD Debugger's IPC socket has no authentication and binds every interface (`INADDR_ANY` in its
  `win32_socket.c`; `--ipc_addr` only affects the sending side). Aero starts a session only when Windows Firewall is
  on in every profile, blocks incoming connections by default and has no rule letting `raddbg.exe` in; it checks
  again before every command and ends the session if that changes (for example after someone chooses *Allow* when
  Windows asks). Aero never edits firewall rules. Only debugging commands are sent (`launch_and_run`, `attach` and
  the like are not on the list).
- Telemetry of the integrated tools is switched off for every program Aero runs (`toolchain.TELEMETRY_OFF`).
