# Aero 1.1: limits, stated plainly

## Background app control

- **No Windows API gives an ordinary app its own keyboard.** Aero works in the background only where an app answers
  UI Automation or Win32 control messages. Chromium/Electron apps (Discord, Slack, VS Code, Spotify), UWP apps and
  games usually ignore posted input; Aero detects that (the window doesn't change) and says so. Doing it anyway
  needs the real mouse and keyboard, which needs your permission each time (or for the task), waits until you stop
  typing, and is refused entirely under Strict Background Only.
- **Some UI Automation providers steal focus.** Measured: the Win32 Edit proxy's `SetValue` and `BM_CLICK` on a push
  button bring the window to the front. Aero avoids both for classic controls and remembers any other
  app/control/pattern that does it. When it happens, Aero tries to put your window back with `SetForegroundWindow`;
  Windows' foreground lock can refuse that, and Aero does not go further (the only route that worked, UI
  Automation's `SetFocus`, injects a keystroke). The result then says your window could not be put back.
- **Pictures:** a minimized window, or a GPU-drawn window that is covered, can't be pictured without bringing it
  forward. Aero gives the control list without a picture instead of a screen grab of whatever covers it.
- **Elevated windows** (programs running as administrator while Aero doesn't) are read-only to Aero. That is
  Windows' UIPI; Aero reports it and does not get around it.
- **Linux and macOS:** no background app control. Desktop control there is the real mouse and keyboard (X11 or
  macOS Accessibility), always behind the foreground-control permission. Wayland-only sessions have no desktop
  control at all, as in 1.0.
- **What counts as "user activity"** is Windows' last-input time. Aero's own real input also updates it; while
  Aero holds the input lock it can't tell your keystrokes from its own.

## Apps

- Discovery reads Start-menu shortcuts, the Installed apps list, App Paths, link handlers and `Get-StartApps`
  (Windows), `.desktop` files (Linux) and `/Applications` (macOS). Portable apps in random folders are only found
  when they have a shortcut or are running.
- A started process is not proof that a page, game or experience finished loading. `app_launch` says which process
  started and which program handled a link; anything more needs a look at the window.
- Store (UWP) apps launched by AUMID can't be started minimized; they may come to the front.
- Programs in Downloads, temp folders or network shares are refused until you allow them.

## Browser

- Aero's browser is its own profile. It is not your browser and is signed in only where you signed in to it. Sign-in
  pages are flagged; Aero never types passwords (password fields are refused).
- Switching between background and visible mode restarts the browser (same profile, other agents' tabs close).
- Content in cross-origin frames is read when the browser allows it; frames it can't read are listed as unread.
  Pages larger than about 1.5 million characters are cut, and the result says so.
- `fetch_url` runs no JavaScript: pages built by scripts need the browser tools.

## Questions and tasks

- A question asked during a reply is answered in the same turn when the agent reaches `get_answer` within 15
  minutes; otherwise the agent finishes what it can and your later answer is sent as the next message in that chat.
  The local model decides when to ask; small models sometimes guess instead.
- Task graphs record what each turn did for the step list, Stop summaries and restarts. They do not re-run work by
  themselves after a restart.
- Verify-before-repeat only covers consequential calls that ended in a timeout: a send that "succeeded" but did the
  wrong thing is not caught.

## Remote Mode

- **Only Windows Remote Desktop (and Linux logind/xrdp) is verified.** RustDesk documents no way for another program
  to know a viewer is connected; Aero shows its connection window as a *probable* sign, which only counts if you
  allow probable signals. AnyDesk, Parsec, Chrome Remote Desktop, Sunshine, TeamViewer and VNC: Aero only sees that
  they run.
- Every switch restarts the model server (llama.cpp can't move layers while running). Replies in progress finish
  first; new messages wait; the KV cache is lost.
- 80 % of the weights on the GPU is not 80 % of the VRAM: on an RTX 5080 with a 27B model it freed 1.75 GB and cut
  generation from 59 to 21 tok/s.
- Real RDP and RustDesk sessions were not tested (no second machine): the session handling is tested with simulated
  sequences only.
- Nothing happens without a GPU, on Apple Silicon, or when RAM can't hold the moved weights.

## Router

- The capability hints are patterns. They only add tools, but they can add unneeded ones (more schema tokens for the
  main model) and miss phrasings they don't cover (3 of 25 held-out requests).
- The bigger tool catalog adds about 0.2 to 0.35 s per router decision on the test CPU.

## Not verified at all

Real Gmail/Outlook accounts, a real Roblox launch, macOS and Linux desktops, AMD and Intel GPUs, multi-GPU Remote
Mode, and a full agent session with a real main model using the new tools. See V1.1_TEST_MATRIX.md.
