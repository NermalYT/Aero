# Aero 1.2: models bigger than the GPU

Workspace **Big models**. Two engines, picked by what the model is:

1. **A GGUF (any quant)** runs in llama.cpp with a plan from `aero/bigmodel.py`: which tensors go to the GPU for the
   VRAM you give it, which stay in RAM, and a small draft model of the same family on the GPU for speculative
   decoding. This keeps every weight resident (VRAM or RAM), so it is the fast path.
2. **A full-precision Hugging Face checkpoint that fits nowhere** runs through **AirLLM** (lyogavin/airllm,
   Apache-2.0): one layer at a time through the GPU, from per-layer files on disk. Every token reads every layer
   from disk, so it is slow; it exists for when quality matters more than speed and nothing else fits.

## What the planner does (`bigmodel.py`)

It reads the GGUF's tensor table (exact byte sizes, 0.15 s for a 54 GB 70B model) and prices each placement:

| Plan | llama.cpp arguments | When |
|---|---|---|
| `gpu` | `-ngl 999` | everything fits |
| `layers` | `-ngl N` (output layer + the last N-1 layers on the GPU) | always possible |
| `ffn` | `-ngl 999 -ot "blk.(0..K).ffn_(up|down|gate).weight=CPU"`: attention and the KV cache of every layer on the GPU, the feed-forward weights of K layers in RAM | dense models |
| `moe` | `-ngl 999 --n-cpu-moe K`: the experts of K layers in RAM, attention, shared experts and router weights on the GPU | mixture-of-experts models |
| `+ draft` | `--spec-type draft-simple -md <draft> -ngld 99 --spec-draft-n-max 8` on top of any plan; the draft's VRAM is taken out of the budget first | a same-family draft exists (`bigmodel.DRAFTS`: Llama-3.2-1B for Llama 3.x, Gemma-3-1B for Gemma 3, Qwen2.5-0.5B for Qwen2.5, Qwen3-0.6B for Qwen3) |

Tied embeddings (Gemma and others store no separate output layer) are counted correctly: llama.cpp puts a copy of
the embedding table on the GPU as the output layer (measured 1,428 MB for Gemma-3-27B Q8_0). When the RAM part is
bigger than free RAM, the plan says so: llama.cpp then maps the file and reads from disk (slow).

## Measured on the test PC (2026-10-11)

RTX 5080 16 GB, Ryzen 9 9950X3D2, 62 GB DDR5, Windows 11, llama.cpp b-current (`AeroTest\llama`), context 8,192,
q8_0 KV cache, flash attention, 16 threads, temperature 0, a 2,200-token summarising prompt and 128 generated
tokens, second run reported. Script: `validation/bench_bigmodel.py`; raw results in `docs/evidence/bigmodel_*.json`.

### Llama-3.3-70B-Instruct Q6_K (53.9 GB) on 16 GB of VRAM

| Plan | VRAM used | Generation | Prompt | Load |
|---|---|---|---|---|
| `layers` (17 of 81 on the GPU), 13 GB budget | 12,432 MB | 1.01 tok/s | 105 tok/s | 29.5 s |
| `ffn` (attention + KV on the GPU, all feed-forward in RAM), 13 GB budget | 12,304 MB | 1.06 tok/s | 96 tok/s | 38.5 s |
| `layers` + n-gram speculation (no extra VRAM) | 12,469 MB | 1.15 tok/s | 144 tok/s | 37.8 s |
| **`layers` + Llama-3.2-1B draft**, 11.5 GB budget for the 70B | 12,690 MB | **4.85 tok/s** | 67 tok/s | 44.7 s |

About 44 GB of the 70B stays in RAM, so every token reads ~44 GB from DDR5: one token a second is the bandwidth
limit, and the two placements are within 5 % of each other at this context length (the `ffn` placement keeps the KV
cache on the GPU, which matters at long contexts). The draft model is what changes the picture: the 70B verifies up
to eight drafted tokens per pass over its weights. The prompt here is a summary at temperature 0, where drafts are
accepted often; free-form chat at higher temperature gains less.

## How to use it

Big models workspace → pick the GGUF → **Plan** (optionally the VRAM to use) → **Load** on the plan you want. When a
draft model exists for the family and isn't downloaded, the workspace offers it. For a Hugging Face checkpoint:
**Install AirLLM** in the pack, then **Run with AirLLM** with the repository name (or a folder) and full precision,
8-bit or 4-bit. The agent can ask for a plan itself (`bigmodel_plan`).
