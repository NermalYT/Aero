# Aero 1.1 performance report

Every number here was measured on 2026-10-09 on one Windows 11 PC (Ryzen 9 9950X3D2, 62 GB RAM, RTX 5080 16 GB,
driver 616.92, llama.cpp 0.6.0-dev build 11501). Raw data is in `docs/evidence/`. Nothing below is estimated
unless it says so; "not measured" means exactly that.

## 1. Router: right tools, and how long it takes

Setup: MiniCPM5-2B Q4_K_M (Aero's recommended router) on the CPU, 8 generation threads, 16 prompt threads, prompt
cache warm, exactly as Aero starts it. Script: `validation/bench_router_intents.py`. A request counts as "routed
well" when the tools the main model ends up seeing (router pick + companions + minimum + 1.1's hints and app tools)
cover every capability it needs. Both versions are scored with the same rules.

| | 1.0.0 | 1.1.0 |
|---|---|---|
| Catalog | 44 tools, 6,123 chars | 53 tools, 7,198 chars |
| Decision schema | 1,237 chars | 1,384 chars |
| Routed well, 50 requests | 29 / 50 | 50 / 50 (in-sample: the hints were tuned after seeing this set) |
| Routed well, 25 held-out requests | 14 / 25 | 22 / 25 (written before, never used for tuning) |
| Decision time p50 / p95, 50 set | 2,224 / 3,143 ms | 2,414 / 3,329 ms |
| Decision time p50, held-out | 1,949 ms | 2,305 ms |
| Tools shown to the main model (median) | 4 | 7 (50 set), 4 (held-out) |

What changed: the router model returned no tools for 17 of the 50 requests on 1.0 ("Remember that…", "Log in to my
bank's website…", "Start Minecraft."). 1.1 adds capability hints (patterns, no model call) and the names of
installed apps found in the message; both only add tools. Cost: about +0.2 to +0.35 s per decision from the larger
catalog, and a few hundred more schema tokens for the main model when hints fire. Held-out misses left: "Close the
dialog in the app I selected", "Turn the volume down", "Fill out the contact form on example.org with my name".

## 2. Remote Mode on an RTX 5080

Setup: a Qwen3.8-27B IQ2_M GGUF (11.5 GB: 64 layers, a 2.4 GB output layer, 521 MB embeddings, one unused MTP block),
8,192 context, q8_0 KV cache, flash attention, no speculative decoding. Script: `validation/measure_remote_mode.py`.
Each configuration was started cold, measured, and stopped.

| | Normal (all layers on the GPU) | Remote Mode (target 80 %) |
|---|---|---|
| `-ngl` | 999 | 53 (planned from the GGUF's tensor sizes) |
| GPU share of weight bytes, planned | 95.32 % | 79.83 % |
| GPU share of weight bytes, measured (llama.cpp's buffer report) | 95.32 % | 79.83 % |
| Model weights on the GPU / CPU | 10,601 MB / 521 MB | 8,878 MB / 2,244 MB |
| KV cache on the GPU | 272 MB | 221 MB (+51 MB on the CPU) |
| Compute buffer on the GPU | 150 MB | 207 MB |
| VRAM used by the model server (nvidia-smi, before vs. loaded) | 11,444 MB | 9,696 MB |
| **VRAM freed** | | **1,748 MB** |
| Load time | 4.2 s | 4.2 s |
| Generation speed (64 tokens) | 58.9 tok/s | 21.2 tok/s |

Findings that shaped the code:
- The naive `floor(0.8 × layers)` would have meant `-ngl 52` here: 78.7 % (measured in an earlier run). It is close
  for this model only because its layers are nearly the same size; the planner uses the real tensor sizes.
- This llama.cpp build offloads the output layer first: `-ngl 30` on a 42-layer model logged "offloading output
  layer to GPU", "offloading 29 repeating layers" and "offloaded 30/43". The MTP block counts as a layer even when
  it isn't loaded. The first plan, made with the older rule, put 0 % of the intended layers on the CPU (VRAM freed:
  122 MB); the corrected model matches the measurement to the hundredth of a percent.
- Buffer sizes are only logged at `-lv 4` on this build. Aero now passes it.
- 80 % of the weights on the GPU cost 64 % of the generation speed for this dense model. Remote Mode trades speed
  for VRAM; it is not free.
- Freeing 20 % of the weights freed 1.75 GB of a 16 GB card, not 20 % of the card.

Not measured: a real remote session's frame rate with and without Remote Mode; MoE models; AMD, Intel and Apple GPUs;
multi-GPU machines.

## 3. Apps, pages and the agent loop

| | Result | How |
|---|---|---|
| Installed-app scan (Windows, this PC) | 222 apps, 392 ms median of 5 forced scans | `app_registry.scan(force=True)` |
| Name resolution | 2.1 ms median, 11.3 ms max (30 lookups) | `app_registry.resolve` |
| App mentions in a message | 1.9 ms median, 4.4 ms max | `app_registry.mentions` |
| Long page (44,575 chars of HTML, 62 sections) | 4.5 ms to extract, dedupe, select and render | `extraction` on a fixture |
| Real browser, background mode | long page read below the fold, table rows, typed value read back, stale ref refused: 2 tests, 2.7 s | `AERO_LIVE_BROWSER=1`, Edge through Playwright 1.63 |
| Three read-only tool calls of 0.4 s each in one step | ran side by side, under 1.1 s in total | `tests/test_v11_agent.py` |
| Background control, foreground disturbances | 0 in 6 live checks (window in front, cursor, clipboard compared) | `tests/test_app_background.py` |

Before the 1.1 fixes, the same live checks measured 2 foreground changes: UI Automation's `SetValue` on a Win32 edit
and `BM_CLICK` on a push button both activated the target window.

## 5. Not measured

- Main-model tokens per second while background jobs run (agent sessions with a real model were not run).
- Router speed on other CPUs.
- Extraction quality on a broad set of real websites (only fixtures and one local page).
- Memory use of Aero's own process over long sessions with the new stores.
