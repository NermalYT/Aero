# Aero 1.2.1: tool calling, prompt inference and the user's own browser

What changed in 1.2.1 so that a request like "look at my GitHub" or "check my emails and look for any
meetings this week" leads to the right actions, and how it was measured. Test PC: RTX 5080 16 GB, Ryzen 9 9950X3D,
62 GB RAM, llama.cpp b11501 (CUDA 13.4).

## What went wrong in 1.2.0

A user asked a local Qwen model to review their GitHub. The chat showed `<tool_call>{"name": "mcp_github_get_user",
…}</tool_call>` as text and nothing happened. Three separate causes, each reproduced:

1. **Tools were off** in that install (`tools_enabled: false`), so no tools were sent; the model wrote a call as text
   anyway. Aero now parses such text calls (and says so with a one-click "Turn on tools" when tools are off).
2. **Text tool calls weren't recognised.** Models write calls in their own formats when the chat template doesn't
   turn them into structured calls: Hermes `<tool_call>`, Qwen3-Coder `<function=…><parameter=…>`, GLM
   `<arg_key>/<arg_value>`, functionary `>>>name`, Mistral `[TOOL_CALLS]`, Llama `<|python_tag|>` and bare JSON,
   Granite `<|tool_call|>`, DeepSeek's `<｜tool▁call▁begin｜>`, Gemma ```` ```tool_code ````. `toolcall_text.py`
   parses all of them (only for tools that are enabled), runs them, and the UI hides the markup.
3. **The model declines to act.** With every tool offered, Qwen3-4B-Instruct answered "I don't have access to your
   GitHub" about half the time (same request, temperature 0.7, 10 tries). `tool_choice: "required"` doesn't help:
   llama-server b11501 only stops the model from ending its turn, so it keeps writing prose; a named
   `tool_choice` is read as "auto" (it logs "Wrong type supplied").

## Prompt inference (`intents.py`)

Before the model sees the request, a set of patterns (no model call, under a millisecond) recognises requests that
plainly need an action and what that action is:

| Request | Plan | First action | On screen |
|---|---|---|---|
| GitHub notifications / pull requests / issues | github.com pages, signed in through Aero's browser | `browser_open https://github.com/notifications` | yes |
| Email, unread, meetings this week | every account: the user's list, mail sites in browser bookmarks, Gmail (`/u/0/`, `/u/1/`…), Outlook; meetings → `meeting_doc` + table | `browser_open` the first account | yes |
| Calendar this week | Google / Outlook calendar week views | `browser_open` | yes |
| Weather, prices, news lookups | `web_search`, `fetch_url` | `web_search` | no (background) |
| IP address, disk space, processes | `run_command` | `run_command` | no |
| What's in a folder | `list_dir` | `list_dir` | no |
| Open an app | `app_launch` | `app_launch` | yes |

"In the background" (or "quietly", "hidden", "without showing") in the request keeps everything out of sight; otherwise
Aero's browser and the apps it uses are on screen. The plan is shown above the work as a chip, the intent's tools
are added to the turn, and the browser closes when the request is done.

Plain chat ("hi", "write a poem", "explain how email works", "mail merge in Word") matches nothing (tested).

## Forced first actions (`forced_call.py`)

When a request needs an action and the model's first reply is a capability refusal ("I can't", "I don't have
access", "as an AI…"; safety refusals are left alone), Aero asks once more with a JSON-schema response format that
can only be one of the allowed tools with valid arguments: `anyOf [{tool: const, arguments: that tool's
parameters}]`. llama-server enforces JSON schemas with a grammar, so the answer is always a well-formed call. The
refusal disappears from the chat and the call runs as if the model had made it.

Measured on Qwen3-4B-Instruct-2507 with Aero's 10 action requests and no hints: 8 of 10 forced calls were right,
0.5 s each. The two misses were GitHub and email, the requests where the right first step is a specific website;
those intents now pass the URL to open as a hint.

## Tool calling in tuning (`tool_eval.py`)

Every tune ends with an exam on the chosen configuration:

- 40 cases from the Berkeley Function-Calling Leaderboard v4 (ShishirPatil/gorilla, Apache-2.0, commit `6ea5797`):
  simple 16, multiple 10, parallel 6, irrelevance 8, graded the BFCL way (right function, every required argument,
  values from the allowed set, no call when none fits);
- 12 Aero requests with Aero's own tools (10 that need an action, 2 that don't).

Short depth runs 12 cases at one temperature; Medium 30; Long and Full all 52 at 0.2 and at the user's temperature,
and also test a runner-up configuration of similar speed. Slow models (under 8 tok/s) get the short exam. The result
sets the temperature Aero uses whenever tools are offered, and `act_first`: when forced first calls beat the
model's own on the Aero requests, Aero forces the first call of an action request straight away instead of waiting
for a refusal.

| Model | Exam | BFCL | Aero requests | Temperature | Forced vs own |
|---|---|---|---|---|---|
| Qwen3-4B-Instruct-2507 Q4_K_M (Full tune, 22 trials) | 79 % | 80 % | 75 % | 0.6 | 70 % vs 70 % |
| Gemma-3-27B-it Q8_0, feed-forward split, 15 GB limit (Short tune, slow-model exam of 13 cases) | 23 % | 0 of 1 | 25 % | 0.2 | 67 % vs 10 % → Aero starts actions |

Gemma wrote 3 of its answers as `print(default_api.list_dir(...))` in code blocks, which that run read as a call to
`print` (a miss). 1.2.1 reads them as the calls they are (`toolcall_text.py`); the exam wasn't re-run after that.

## Hindsight

Hindsight's reflect forces named tools. The loopback adapter in front of Aero's model (`integrations/llm_adapter.py`)
now answers those requests itself with a grammar-forced call, returned as an ordinary `tool_calls` response, streamed
or not; only if that fails does the request go through with `tool_choice: "required"`.

## The user's own browser

Requests like "check my GitHub" need the accounts the user is already signed in to. Aero 1.2.1 works in the user's
default browser (read from the system: the https UserChoice on Windows, LaunchServices on macOS, `xdg-settings` on
Linux; Chrome, Edge, Brave, Vivaldi or Chromium). Two ways:

- **Connected to the running browser** (the default when possible). Since Chrome 144 a user can switch on remote
  debugging for the browser they are using at `chrome://inspect/#remote-debugging`; the browser then writes
  `DevToolsActivePort` into its user-data folder and asks the user to Allow each connection. Aero reads that file
  and connects (the same mechanism as chrome-devtools-mcp's `--autoConnect`, Apache-2.0). It opens its own tabs,
  sees and closes only those, and disconnects when the request is done; the browser and the user's tabs stay.
  Measured against a throwaway Chrome 155 started with remote debugging: Aero saw 1 of the 2 open tabs, closed its
  own, and the browser kept running with the other tab. The browser's own Allow prompt was not exercised in testing
  (it needs the user's click).
- **Aero's own profile** of that browser, when the switch is off, the user declines, strict offline is on (Aero can't
  police another browser's traffic) or the request says "in the background". The sign-in card then says how to switch.

Aero never copies the browser's profile or decrypts its cookies: Chrome binds them to the profile on purpose, and
working around that is what credential-stealing malware does.

## Not done

- Embedding-based tool retrieval (picking tools by similarity instead of the router) was looked at; the router plus
  intents cover Aero's catalog of 53 tools, so it isn't in 1.2.1.
- Firefox and Safari as the user's own browser: Playwright drives Chromium only, so with those as the default Aero
  uses an installed Chromium browser with its own profile.
